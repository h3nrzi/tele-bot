# 06: Admin approval + double-entry Ledger

**What to build:** An Admin taps the **Approve** inline button on a pending receipt notification. The bot immediately credits the Buyer's Wallet with the full USD amount, records two immutable Ledger Entries (a debit to `SYSTEM_CASH` and a credit to `BUYER_WALLET`), marks the Top-Up Request as `APPROVED`, and sends the Buyer an instant notification confirming the credited amount and their new Available Balance. If two Admins tap **Approve** simultaneously, exactly one succeeds — the other sees "already processed" — and the Buyer is credited exactly once.

**Blocked by:** 05 — Receipt submission + Admin push notification

**Status:** done

- [x] Drizzle migration creates the `ledger_transactions` table (`id` UUID PK, `top_up_request_id` UUID FK → `top_up_requests` nullable, `narrative` TEXT NOT NULL, `created_at` TIMESTAMPTZ NOT NULL) and the `ledger_entries` table (`id` UUID PK, `ledger_transaction_id` UUID FK → `ledger_transactions` NOT NULL, `account_type` ENUM(`BUYER_WALLET`,`SYSTEM_CASH`) NOT NULL, `direction` ENUM(`DEBIT`,`CREDIT`) NOT NULL, `usd_amount` NUMERIC(18,2) NOT NULL, `wallet_id` UUID FK → `wallets` nullable, `created_at` TIMESTAMPTZ NOT NULL). No UPDATE or DELETE is ever issued against either table.
- [x] Admin approval service executes the following steps inside a single PostgreSQL transaction: (1) `SELECT … FROM top_up_requests WHERE id = ? FOR UPDATE`; (2) assert `status = 'PENDING'` — if not, abort and return an "already processed" error without writing any ledger rows; (3) `SELECT … FROM wallets WHERE user_id = ? FOR UPDATE`; (4) insert one `ledger_transactions` row; (5) insert two `ledger_entries` rows — `DEBIT SYSTEM_CASH` (no `wallet_id`) and `CREDIT BUYER_WALLET` (`wallet_id` set) — both for the same `usd_amount`; (6) `UPDATE wallets SET available_balance = available_balance + usd_amount, updated_at = now()`; (7) `UPDATE top_up_requests SET status = 'APPROVED', processed_by_admin_telegram_id = ?, processed_at = now()`.
- [x] All USD arithmetic inside the service uses `decimal.js`; the updated `available_balance` written to the DB is `.toFixed(2)`.
- [x] The Buyer's `available_balance` never goes negative as a result of an approval (credits only increase it in this RFP).
- [x] Inline **Approve** callback handler: verifies the caller is an Admin (via middleware), extracts `top_up_request_id` from callback data, calls the approval service, and edits the original Admin notification message to show the outcome (approved or already processed).
- [x] Buyer push notification: sent after the transaction commits. Message includes the credited USD amount and the Buyer's new Available Balance. Failure to send does not roll back the transaction.
- [x] Approval service tests cover: happy path — two `ledger_entries` rows written, `available_balance` increased by exactly `usd_amount`, request status is `APPROVED`, `processed_by_admin_telegram_id` and `processed_at` are set; multi-Admin race — two concurrent calls for the same request result in exactly one `ledger_transactions` row and two `ledger_entries` rows, the second call returns "already processed"; ledger self-balance invariant — for every `ledger_transactions` row, the sum of CREDIT `usd_amount` equals the sum of DEBIT `usd_amount`.
- [x] No test calls the Telegram notification API; notification dispatch is injected as a dependency and stubbed in tests.
